# Change specifications and shape commands

Read the [command reference](commands.md) for shared invocation, freshness,
and plan/approve/apply requirements before using these specifications.

Exact human gates below may be delegated under explicit
[YOLO authorization](yolo-mode.md) for the current task only. Ordinary auto
allocation limits are unchanged; semantic ambiguity, source preservation and
full-tree checks remain blockers in every mode.

## Complete split spec

```json
{
  "id": "feature",
  "title": "Feature work",
  "remote": "upstream",
  "target": "trunk",
  "source": { "base": "<integration-commit>", "head": "<source-commit>" },
  "backup": { "enabled": false },
  "nodes": [
    {
      "id": "model",
      "title": "Introduce the shared model",
      "description": "Fill the repository's PR template for this change.",
      "dependencies": [],
      "change": {
        "base": "<comparison-commit>",
        "head": "<source-commit>",
        "paths": ["src/model.ts"]
      },
      "validations": [
        { "command": "node", "args": ["--test", "test/model.test.mjs"] }
      ]
    },
    {
      "id": "consumer",
      "title": "Use the shared model",
      "description": "Standalone description for the consumer change.",
      "dependencies": ["model"],
      "change": {
        "base": "<comparison-commit>",
        "patch": "diff --git ...\n"
      },
      "validations": [],
      "validationReason": "Documentation-only; no applicable automated check."
    }
  ]
}
```

Replace all placeholders; `patch` must be a real full-index Git patch, not
`diff --git ...`. See [change representation](graph-and-changes.md).
For repositories restricting branch namespaces, set `helperBranchPrefix` in
the complete graph spec, for example `"user/alias/feature-bases"`. Prerequisite
bases use `<prefix>/<node-id>`; the default remains `pr-graph/<graph-id>/bases`.
Changing the prefix requires an approved shape plan (such as `deps`) and
separate publication. It preserves unchanged node commits and retains old
helper refs; it does not rename or delete them.
When no remote exists, omit it and supply a target. Multiple remotes need an
explicit selection. The target need not be `main`.

For local-only behavior with a hosted remote:

```json
{ "provider": { "kind": "local" } }
```

For GHES, specify `"provider": { "kind": "github" }`; host/owner/repository come
from the chosen remote URL, not a hard-coded hostname.

`source.base` must equal the pinned integration target for `split`. The complete
combined result must match `source.head` exactly. Prepare a behind-target source
explicitly rather than weakening the losslessness check.

Each node needs a stable ID, title, own change, prerequisites, and either
validation argv arrays or a specific reason why no automated check applies.
Descriptions are authored by the agent, not generated by the helper.

## Shape actions

| Action       | Spec and behavior                                                                                                                    |
| ------------ | ------------------------------------------------------------------------------------------------------------------------------------ |
| `init`       | New graph from a complete spec; optional source reconstruction gate                                                                  |
| `split`      | New graph; requires exact source reconstruction                                                                                      |
| `add`        | Existing graph plus a complete active-node spec; existing own changes immutable                                                      |
| `deps`       | Complete active-node spec; existing own changes immutable; update edges/validation configuration                                     |
| `split-node` | Complete replacement spec with `supersedes`; preserve combined tree                                                                  |
| `fold`       | Complete replacement spec with `supersedes`; preserve combined tree                                                                  |
| `remove`     | Complete remaining active-node spec; retire omitted nodes; explicitly changes combined tree                                          |
| `absorb`     | Complete active-node spec plus pinned follow-up and per-unit allocations; preserve identities/edges and verify the approved new tree |

Omit previously retired nodes from specs. Their snapshots and IDs remain
reserved. Nodes omitted by split/fold/remove become retired rather than losing
their content. Active descendants cannot depend on an unlanded retired node.

For example, folding A+B into AB:

```json
{
  "id": "feature",
  "nodes": [
    {
      "id": "ab",
      "title": "Combine the model changes",
      "dependencies": [],
      "supersedes": ["a", "b"],
      "change": { "base": "<base>", "head": "<combined-commit>" },
      "validationReason": "Specify applicable checks or a real no-check reason."
    }
  ]
}
```

Splitting AB into A2+B2 maps both new nodes to `"supersedes": ["ab"]`.
Retaining the original node ID is allowed while changing its own selection in a
split/fold, but explicitly map any retired identities. Retired IDs cannot be
reused.

To adopt a same-repository PR in `init`/`add`, supply its existing branch and
`"adoptPr": <number>` on the node, plus an explicit own-change selection. The
helper verifies PR identity rather than inferring a multi-parent graph from
base branches.

## Allocate follow-up edits with absorb

Absorb is an explicit extension for adding approved follow-up edits, not an
exception to split/fold preservation. It preserves all node IDs, branches,
supersedes mappings, and dependency edges. It does not create or retire nodes,
change helper namespaces or backup configuration, or modify landed own changes.
If a semantic decision needs new identities or edges, prepare separately
approved add/split/fold/deps transformations first, then inventory again.
Never silently attach leftovers to the latest node.

Select an already-committed base/head explicitly. The base's **complete tree**
must equal the current graph's combined tree; the head is the intended combined
result including only the selected follow-up edits. This supports a source
whose commit identity differs but tree is identical. The helper does not stage,
commit, stash, or snapshot dirty input. If preservation is needed, use the
separately approved checkpoint workflow and separately authorize any staging.
An unsuitable or behind-target source needs explicit preparation, not a weaker
tree check.

```text
node "<helper>" absorb --repo "<repo>" --graph feature --base "<combined>" --head "<follow-up>"
```

This read-only inventory returns pinned commits, the full follow-up patch,
expected full-tree ID, graph digest, retained own-patch provenance, and stable
digest IDs for each hunk. Binary content, additions/deletions, mode changes and
other non-text changes are whole-file units. Renames are explicit delete/add.
Path-based `candidates` and a unique active-path `suggestedOwner` are evidence
only; every `owner` remains null. Shared/unknown paths and indivisible units
have no suggestion. Retained landed/retired provenance is labeled, never an
automatic destination.

The agent inspects each hunk's surrounding behavior, retained own patches,
history/provenance and dependency/consumer context. Propose an owner with
specific evidence and rationale. Inspect cross-node refactors, new/shared files,
binaries and landed/retired provenance explicitly; leave ambiguous same-file edits
or conflicting ownership unassigned until the user makes a semantic decision.
A nearest-line or path-only match is not semantic ownership. A user can explicitly assign an
indivisible unit to an active owner, or choose separate restructuring; never
rewrite a landed/retired node or infer an edge. Approval of an allocation
proposal alone does not approve application. In auto mode, an unambiguous owner
may be selected from semantic evidence, including for a whole-file unit; do not
turn an indivisible change or a path suggestion into an automatic assignment.

Prepare a complete active-node spec containing the replacement own changes,
validation argv/reasons, and these additional fields:

```json
{
  "id": "feature",
  "source": { "base": "<pinned-integration>", "head": "<follow-up-head>" },
  "followUp": { "base": "<old-combined>", "head": "<follow-up-head>" },
  "allocations": [
    {
      "unit": "<inventory-hunk-digest>",
      "node": "model",
      "evidence": "Identify the retained own patch and relevant behavior.",
      "rationale": "Explain why this owner, not a consumer or another candidate."
    }
  ],
  "nodes": [
    {
      "id": "model",
      "change": { "base": "<own-base>", "head": "<amended-own-head>" },
      "validations": [
        { "command": "node", "args": ["--test", "test/model.test.mjs"] }
      ]
    },
    { "id": "consumer" }
  ]
}
```

Replace placeholders and include every active node and **every unit exactly
once**; the short example is illustrative, not an executable complete spec.
Omitted node fields inherit current values, but inspect the helper-normalized
complete payload. An unassigned/duplicate/unknown unit blocks planning. Owners
must be active and unlanded, with nonempty evidence and rationale. Unassigned
nodes' own changes stay immutable. `source.base` is the integration snapshot;
`source.head` must equal the pinned `followUp.head`.

```text
node "<helper>" plan absorb --repo "<repo>" --graph feature --spec "<spec.json>" --out "<new-plan.json>"
node "<helper>" apply --repo "<repo>" --plan "<new-plan.json>" --yes --approve "<digest>"
```

Review the exact plan before approving: full old/new own changes, allocations
and rationale, preserved identities, empty dependency changes, affected owner
and descendant closure, validations, pinned expected source/tree, local branch
effects and anticipated separate publication. Use a new external plan file for
each revision; neither proposals nor old digests authorize changed payloads.

Application reconstructs the original graph and verifies the follow-up base.
For each owner, it applies the allocated hunks to that node's old realized head
and separately applies the proposed own change to its old realized base. Those
complete trees must match: matching the final combined tree alone cannot hide
allocation to the wrong node. Hunks sharing a file/owner are applied together
in inventory order. Context that cannot transport independently is a conflict,
not authority to invent an edge or resolution. An empty resulting own change
needs separate restructuring rather than an implicit node removal.

The helper reconstructs affected owners and descendants using normal
prerequisite closures, verifies the final complete Git tree equals the approved
follow-up head, and runs required validation before product ref updates.
Unchanged snapshots/checks can be reused by existing exact-signature rules.
Input/graph/ref drift invalidates approval; conflicts, hooks and failed checks
retain normal recovery journals/worktrees. Occupied graph branches are rejected,
not moved, and unrelated dirty files and the index are untouched.

Absorb is local-only: no pushes, PR/footer/draft writes, readiness, or backup
uploads. Existing hosted content remains unchanged until separately authorized
publication/sync. New local heads invalidate readiness/validation as normal.
Human approval of the exact absorb plan is required unless the skill's
[conditional auto-absorb policy](auto-mode.md#conditional-auto-approvals) applies:
allocation is requested, every owner is unambiguous and evidence-backed, and
all attribution, preservation and validation gates pass. Ambiguity still needs a
user decision. Checkpoint, recovery, publication, readiness and merge retain
their own gates; absorb does not broaden them.
